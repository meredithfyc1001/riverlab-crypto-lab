# RiverLab Crypto Lab — 产品与开发计划

> 版本：规划 v0.1 ｜ 日期：2026-10-18 ｜ 状态：待 Codex 启动
>
> 定位：中文、Windows 优先、浏览器可用、离线优先的加密资产历史数据分析与策略研究工具。仅做研究与模拟，不提供实际交易、资金托管、充值提现、信号跟单或代客理财。

## 0. 项目原则

1. **研究优先**：目标是验证策略是否有统计优势，不是承诺赚钱，不依据单次回测给出实盘建议。
2. **零真实资金**：全部模拟本金用虚拟单位计价，默认 1000 虚拟 USDT；首发版绝不连接真实账户或创建交易订单。
3. **离线优先**：历史行情由用户手动导入 CSV/ZIP，核心研究功能断网可用，不依赖 Binance 登录或 API Key。
4. **合规优先**：面向位于中国内地的开发者，避免开发境内受禁止的虚拟货币兑换、撮合、交易相关金融业务；发布/联网/服务范围变化前重新核查法律。
5. **精度优先**：严防未来函数、偷看未来、幸存者偏差、错误成交假设和参数过拟合。凡影响结果的假设必须在界面明示。
6. **与 GTO 项目隔离**：新建独立仓库；沿用 AGENTS.md、plan.md、progress.md、PR、分阶段验收的流程。
7. **可复现**：每次回测保存算法版本、数据标识/哈希、策略参数、成本假设、种子（如适用）与运行时间。

## 1. 产品目标与适用用户

- 核心用户：愿意学习量化研究、拥有有限试验预算、重视风险教育的个人。
- 首要任务：导入一段 BTCUSDT/ETHUSDT 真实历史行情，选择策略和参数，得到可解释、可复现的回测结果。
- 次要任务：评估风险参数对结果的影响、比较策略与买入持有、在历史回放环境中练习模拟决策。
- 非目标：预测下一根 K 线涨跌、提供盈利保证、自动下单、高频实盘交易、规避平台地区限制、管理真实资金。

## 2. 主要页面

1. **工作台**：数据集、最近实验、摘要、使用引导与风险提示。
2. **数据中心**：导入、校验、日期区间、周期、缺失 K 线、重复与时区问题、数据出处。
3. **行情中心**：OHLCV K 线、成交量、技术指标、策略买卖点。
4. **策略中心**：策略列表、参数配置、策略说明与版本。
5. **回测中心**：运行配置、交易事件、净值曲线、基准对比。
6. **风险中心**：最大回撤、回撤持续时间、连续亏损、风险暴露、压力情景。
7. **实验中心**：保存、加载、比较、导出 CSV/JSON/HTML 报告。
8. **历史回放**（后续）：逐根播放、虚拟下单、复盘笔记。

## 3. 推荐技术方案（由 Codex 在阶段 0 验证后确定）

- Web 前端：React + TypeScript + Vite，中文界面，深色主题优先，可切换浅色主题。
- 可视化：性能良好的 K 线图组件与常规统计图；避免所有计算绑死在 UI 图表中。
- 策略与回测核心：独立、纯 TypeScript 模块，不直接依赖 React；确定性事件/逐 K 线驱动；模块间接口稳定。
- 测试：Vitest 单元测试 + 数据导入/回测集成测试 + 至少一条浏览器 E2E 烟测。
- 存储：先用浏览器本地能力与文件导出/导入；确保隐私、兼容性和容量限制有明确回退方案。
- 发布：先跑通本地开发模式与静态打包；验证 Edge/Chrome 离线运行。后续需要单 HTML 文件时，单独做可验收的单文件发布，不依赖 `file://` 下通常受限制的原生模块加载方式。
- 数据解析：大数据导入用流式或 Web Worker；时间戳统一规范化到 UTC 毫秒，使用显示时区转换；金额计算避免浮点累积误差。
- 代码质量：TypeScript strict、格式化、lint、测试、构建，按 PR 自动检查。

### 数据源策略

- **MVP**：用户手工导入真实历史 K 线 CSV；内置有显著“人工合成数据”标记的演示数据。
- **第二步**：可导入官方公开历史数据归档 ZIP（例如 Binance Public Data）的 Spot Kline 数据；无需 API Key。
- **以后可研究**：市场公开数据只读接口作为可选能力，但是否提供联网拉取须先独立完成地区合规、使用条款、故障/限速检查。即使不能联网，离线分析必须完整可用。
- **重要兼容性**：Binance Public Data 的现货历史归档自 2025-01-01 起使用微秒时间戳；不能把所有时间列都当作毫秒处理。导入器需检测或明确指定单位并严格测试。
- 导入校验：字段映射、时间严格递增、重复时间戳、负数价格/成交量、OHLC 逻辑、周期完整性、停牌/缺失区间、UTC 与本地时区分离、无效行报告。

## 4. 回测引擎正确性规格（必须项）

1. **无未来函数**：仅用当前及过去已完成的 K 线计算信号；默认在当前收盘形成信号、下一根开盘模拟成交，不能用未来数据决定当下交易。
2. **成交规则透明**：市价/限价（限价以后做）；手续费、双边滑点、最小交易金额/精度作为可配置假设。
3. **初版只做现货、多头、单一币种、无杠杆**；不能透支余额、不能出现负持仓数量。避免在第一版混入合约保证金逻辑。
4. **止盈止损**：遇到 K 线内同时触及止盈与止损时，使用明确标注的保守假设，不把不存在的 K 线内顺序当作已知事实；跳空与滑点明确处理。
5. **逐笔账本**：每个成交的日期、原因、成交价、数量、成本、现金、持仓、权益可追溯；最终收益与权益变化可对账。
6. **指标口径**：收益率、年化（满足足够数据才显示）、最大回撤、最大回撤持续时间、胜率、盈亏比、利润因子、交易数、暴露时间、买入持有基准；不足样本展示 NA 和原因。
7. **基准公平**：同区间、同初始本金、注明基准是否计算费用。
8. **数据质量门槛**：缺失/损坏数据时警告或阻止回测；不默默补齐高频价格。
9. **一致性**：相同数据/版本/配置必须产生相同结果；UI 不得篡改回测原始统计。
10. **明确警告**：历史回测收益不是未来回报；回测忽略真实流动性、盘口冲击等复杂因素，数据粒度越低误差可能越大。

## 5. 分阶段迭代与交付标准

### Phase 0 — 仓库与基础工程（建议 PR #1）

**交付**：独立仓库 `riverlab-crypto-lab`（名字可调整），React/TypeScript/Vite 脚手架，基础页面框架，中文 UI 主题，文档，CI，示例数据标记。

**验收**：开发启动、生产构建、类型检查、lint、测试全通过；运行示例；Edge/Chrome 打开；无账户登录/真实交易功能。建立 `AGENTS.md`、`plan.md`、`progress.md`。

### Phase 1 — 数据中心与 K 线图（建议 PR #2–3）

**交付**：CSV 导入、列映射、UTC 时间处理、数据质量报告、BTC/ETH 样例、K 线/成交量/MA EMA RSI 基础展示；可保存和再次打开数据。

**验收**：真实样本 + 错误样本测试；正确识别毫秒/微秒；缺失数据有清晰提示；断网仍可使用已导入数据；大文件不使界面卡死。

### Phase 2 — 回测 MVP（建议 PR #4–6，形成 V1.0）

**交付**：统一回测引擎，双均线、RSI 阈值、价格突破三种策略；虚拟本金、手续费、滑点、止盈止损；交易账本、收益曲线、基准比较、回撤图与导出报告。

**验收**：至少覆盖上涨、下跌、横盘、跳空、双触发止盈止损、空数据、重复数据等固定测试案例；策略信号生成与下单执行隔离；无未来函数；金额可对账；相同配置结果完全一致；体验全流程 1 次。

### Phase 3 — 风险分析与策略比较（建议 PR #7–8）

**交付**：多策略批次运行、参数敏感度热力图、收益/回撤比较、样本内/外拆分、滚动测试、过拟合警告。

**验收**：测试集严格晚于训练集；调参不能偷偷引用测试集；明确显示模拟交易成本；不能用单一收益指标自动宣称“最佳策略”。

### Phase 4 — 历史回放与模拟账户（建议 PR #9–10）

**交付**：历史逐根播放、虚拟买卖与余额、交易日记、模拟净值与风险看板、保存/恢复回放状态。与策略回测共享同一成交模型。

**验收**：播放时不暴露未来 K 线；余额不为负；交易日志和权益可对账；中断与恢复无差异；不触达真实资金。

### Phase 5 — 高级研究功能（V2.0，按优先级）

**候选**：可视化条件策略编辑器；多币种组合；Monte Carlo 风险分析；不同市场状态识别；可复现实验档案；高性能批量回测；离线单文件/可选桌面封装。

**延后**：杠杆、期货、资金费率、强平与更复杂的多资产撮合模型，单列独立研究规格，不能把现货模型简单乘以杠杆倍数。

## 6. 里程碑闸门（不通过不推进）

| 里程碑 | 是否可正式迭代下一阶段的门槛 |
| --- | --- |
| M0 基础项目 | CI 绿灯；文档存在；Windows 运行通过 |
| M1 数据可用 | 真实历史数据导入正确；毫秒/微秒无错；数据质量警报有效 |
| M2 可信回测 | 无未来函数；费用/滑点正确；逐笔对账；固定案例通过 |
| M3 研究工具 | 策略对比与样本外评估可复现，避免过拟合的提示明确 |
| M4 模拟回放 | 无真实交易连接；不能看未来；断点恢复准确 |
| M5 正式版本 | 浏览器兼容、备份恢复、离线测试、使用说明、风险说明完整 |

## 7. GTO 项目经验迁移

- **同一节奏**：一个可审查 PR 对应一个可验收的小阶段；由用户先在 Windows 上实际测试，再合并。
- **同一文档体系**：`AGENTS.md` 管开发约束，`plan.md` 管路线和验收标准，`progress.md` 管已完成/问题/下一步。
- **控制自动发布风险**：Codex 优先自动执行其可用的改动和 PR；提交权限或环境限制导致自动发布失败时，保留可复制、可复现的手工方案，但不重复无效尝试。
- **独立 repo**：不混用 GTO 的源码、CI、数据与策略模型；共用研发经验，不共用业务逻辑。
- **验收记录**：每次用户测试按“通过/失败/未测试”逐项更新，而不是把 Codex 自测当作全部完成。

## 9. Codex 开始开发时的第一轮任务说明

> 先只做 Phase 0。完整阅读本 `plan.md`，列出实现拆解、风险和验收命令。创建独立仓库/分支（若无 GitHub 权限则在当前工作区准备可提交内容），搭建基础工程与文档，完成测试/构建/运行说明，形成一个可审查 PR。**不要提前开发交易连接、回测大引擎、实时数据抓取或高阶策略功能。** 不得声称没有实际执行过的测试已经通过。完成后更新 `progress.md`，报告文件改动、执行命令、测试结果、遗留问题与下一阶段建议。若无法自动推送，提供最小化手工发布步骤。

## 10. 实际使用安全边界

- 不接收用户的 Binance API Key、密码、验证码、助记词、私钥。
- 任何演示交易使用虚拟账户与虚拟本金，禁止真实订单请求或自动下单。
- 数据文件仅本地保存；未来引入外部接口前重新评估中国内地监管、平台地域条款和数据使用许可。
- 强制显示“历史表现不代表未来表现”“仅供学习研究”“不提供投资建议”。
