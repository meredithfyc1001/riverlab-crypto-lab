# Phase 5E 容量评估与安全审计

生产容量维持单币种 **50,000 根**、组合所有原始快照合计 **10,000 根**、组合与高级研究 JSON **32 MiB**。现有的 50,000 根单币回测在三次本机抽样中耗时 3.04–4.47 秒。完整市场状态研究的浏览器进程 RSS 采样达到约 1.09 GiB。在扩容目标上仅验证了分片数据处理成本和原准入检查。单币 100,000 根及组合 50,000 根的整体成交、报告恢复、取消和跨浏览器内存验收仍待完成。

## 高级研究并发

50,000 根 RC 合成行情，训练和测试各 25,000 根，各窗从空仓独立起算。MA 交叉的买入快线在 1–3 之间搜索，PCG32 种子 27，不放回抽取 3 个候选。一次研究实际运行 3 次训练、1 次锁参测试，共求值 100,000 根次。申请 4 个 Worker 后按原始快照和最长窗口预算使用 2 个。另跑同一研究的单 Worker 版本并逐项比对整个 result。两次得到相同的结果，测试窗完成 2,082 笔交易。调度进度收到首个完成的候选后进行取消检查，取消耗时测到前台 promise 拒绝。重跑成功后从实际下载文件交给另一独立浏览器配置重算。[测量场景](../tests/performance/capacity/advanced.ts)

## CSV、数据库与扩容目标

专用页面通过实际 CSV Worker 解析、计算原文件 SHA-256、校验和回传行情，调用 DatasetStore 提交 IndexedDB 事务并读回逐根校验。每个合法分片各走一次 V1 备份编码与解码，另断言重导结果逐字节一致。不同场景使用独立浏览器配置。以下是初轮 Linux 组件测量，各分片顺序执行，耗时为各分片之和，字节数含每个分片自己的头部。100,000 根使用同一交易对连续的两片，50,000 根组合使用五个 UTC 对齐的不同交易对。主线程堆列是分片完成及准入检查后的离散采样上界。[容量脚本](../scripts/profile-capacity.mjs) · [测量输入及校验](../tests/performance/capacity/sample.ts)

## 独立扩容方案

1. 用同一批稀疏成交和密集成交样本，在独立分支分别评估单币输入与组合报告。保留原 50,000 / 10,000 门槛回归，增加目标量、目标加一根、输入刚好和超出字节边界、选区较短而原始快照超限的用例。按 CSV 字节、原始根数、求值总根次与同时存活的副本数分别准入。
2. 对单币测试可转移的列式数值缓冲及按需交付曲线。保持 UTC、规范十进制与 18 位定点账本语义，用原逐笔成交、权益和整份 Hash 做等价验证。测量编码、线程交付、图表和 IndexedDB 原子提交，单列数据备份的 20 MiB 和 CSV 的 10 MiB 约束。
3. 分别对固定子账户、策略共享、逐根调仓压测两币与五币。历史两币 10,000 根密集调仓的原始组合报告已达 11,619,964 字节，五币为 8,983,494 字节。5 倍根数对 32 MiB 的余量构成直接风险。评估流式规范编码和分块账本的版本化格式，旧格式仍按原 Hash 重算；在达到内存预算前中止构造并保留用户原件。[原始组合满载证据](phase-5c-b-review.md)
4. 在 Ubuntu Chromium、Windows Chrome、Windows Edge 以全新配置至少重复三次各阶段。分别记录运行、密集进度中取消、主线程采样间隔、JS 堆、进程 RSS、报告大小、保存、JSON 导出和清空配置后恢复/重导。覆盖两种并发设置、低存储配额和取消后立即重跑。保留现行时限与全部版本复现回归。按实测结果分别决定单币、组合限额。
