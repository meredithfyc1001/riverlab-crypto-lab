# Phase 5D 报告库列表故障复核

## 修复前的复现

受测提交为 `e580125d8adf15d1aca947ec8b500ad6a8e77952`，测试使用 Node 24、锁文件中的 fake-indexeddb 和一个全新的内存数据库。用 `git archive` 提取该提交的存储层和内核，在隔离目录运行以下步骤。

1. 在单币种实验库存入 `windows-20261125/ma-2-4.json` 与 `rules-v1.json` 的正式记录，在固定组合库存入 `phase-5c-a-synthetic.json.gz`，在共享库中各存一份冻结的策略共享和定期再平衡报告。五条来源都可通过市场状态研究入口使用的 `listRegimeSources()` 列出。
2. 依次以单币种 MA、规则 V1、MA 为源创建三份 5D 报告。固定观察周期 2、阈值 500 基点、参考资产 null，元数据取 `id=regime-a/b/c`、`name=probe a/b/c`、`createdUtcMs=1800000000000`，观察时间取同一毫秒值。保存后三份摘要都可列出。
3. 用单独的测试写事务仅将共享库再平衡记录的摘要 `name` 改成空字符串，正文保留原样。随后 `listRegimeSources()` 抛出“组合实验身份、名称或时间无效。”。单独枚举单币种、固定库仍分别得到 2 和 1 条健康摘要。共享库物理上仍有 2 条摘要，另一个共享实验也随整张列表失去可见性。
4. 以同样方式仅将 5D 的 `regime-c` 摘要名称改为空字符串。随后 `MarketRegimeStore.list()` 抛出“市场状态报告摘要损坏。”。实际从同一库通过 `load(id)` 读取另外两份正文，经 `verifyRegimeReport` 完整重算，所得对象与原件深度相等。再次导出的紧凑 UTF-8 JSON 与注入损坏前的原件逐字节相同。

| 按 ID 读取的健康报告 | 重算及导出时的原报告 SHA-256                                       | 导出 JSON 字节 |
| -------------------- | ------------------------------------------------------------------ | -------------: |
| regime-a             | `0bf2dc5e3ffd014117178ad009f7b7a3694852ec5838dbba7d86cce6f3f95ebc` |          8,511 |
| regime-b             | `7b8348ffabfcd059a8afe14d2806f77cd3cbc9a5826bdea652839668ab6d7d2e` |          8,889 |

复现前后，依次读取单币、固定、共享、5D 的正文明细，在各库内按 IndexedDB 主键顺序排列。对这四组数组整体做紧凑 JSON 编码并计算 SHA-256，两次均为 `126fa32e3fa1525f48b24ee7286a89c0632926def92671e313b10d4e23d9ff3f`，共八份正文。复现结束时两个被修改的摘要均仍在库中，名称均为空字符串。

## 根因和检查范围

原提交的 `PortfolioStore.list()` 读取全部摘要，再以 `forEach(assertPortfolioSummary)` 逐行验证，首个异常导致整个列表 Promise 拒绝。共享库复用该实现。5D 的 `listRegimeSources()` 以 `Promise.all` 合并单币、固定和共享三个列表，其中任意一个拒绝就会丢失其余库已成功返回的数据。5D 自己的 `MarketRegimeStore.list()` 同样在全量读取后执行 `forEach(checkSummary)`。这些异常发生在列表形成阶段，按 ID 查询健康正文仍可成功。

| 原提交的入口                            | 发现                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 5D 的单币、固定组合、共享来源及已存研究 | 单币来源使用整组 `some` 验证，固定和共享使用整组 `forEach` 验证，已存研究使用独立的整组 `forEach` 验证。均直接影响 5D 选择器。 |
| 风险研究、历史回放                      | 两者分别以 `some` 检查所列摘要，任一坏行会使该入口整体拒绝。                                                                   |
| 数据集、规则版本                        | 数据集循环验证整组摘要。规则库逐个验证完整规则版本，单项出错时本次列举也会中止。                                               |
| Phase 3 策略研究                        | 没有独立的持久化研究报告列表。                                                                                                 |

原数据库事务在 complete 事件后返回值，中止及打开失败会拒绝。逐行摘要校验和数据库整体不可读属于两个故障层级。后者需要向用户传达库级错误，不能推断该库为空。此次定位涉及市场状态研究页面消费的四类列表；独立的风险、回放、数据集及规则入口记录为后续可单独处理的同类风险。

## 修复后的对照

复用上述五份来源和三份研究报告。共享库成功列出 1 条摘要，隔离 1 条；另外两个源库分别列出 2 条和 1 条。5D 报告库列出 2 条，隔离 1 条。两份健康报告经原 Worker 验证路径重算并导出，完整 JSON 与原件逐字节一致，CSV 携带同一报告 Hash。再次读取全部八份正文，联合 SHA-256 与上述值一致。被隔离的摘要保留在原数据库。

摘要通过字段校验后才进入列表。正文按使用时机在 Worker 内验证；有效摘要对应的损坏正文在重开、研究或导出时仍会被拒绝。库级错误与记录级诊断分别保留。测试涵盖单库及所有源库拒绝打开、5D 库打不开，以及 getAll 请求已成功但事务随后中止，界面分别显示受影响库的错误。报告生成、盈亏归因、版本、数据布局和历史 Hash 算法沿用原实现。其他功能页的列表策略见上表。

生产浏览器与 Windows 解压验包均使用临时空配置，先经正常界面保存报告，再定向注入摘要和正文故障。操作后比较各库原始记录。单元回归另锁定修复前实测的两份完整报告 Hash、JSON 字节数和全部八份正文的联合摘要。[单元回归](../tests/unit/market-regime-library.test.ts) · [浏览器回归](../tests/e2e/market-regime-library.spec.ts) · [最终提交 CI 与验包记录](https://github.com/meredithfyc1001/riverlab-crypto-lab/pull/14)
